A file with an identical twin could keep the wrong content in a backup

Present in every release from 2.1.0 to 4.2.15, including the versions published under the name fast-copy. Fixed in 4.2.16.

What went wrong

When two source files have the same content, blitcp copies one and links the other to it at the destination. That is the deduplication that is on by default. Two faults in how a later run handled those linked files could leave a file in the backup with the wrong content, while the run printed “All N files are already up to date” or “Verified: all N files OK” and exited 0.

1. A twin whose path already existed was skipped. If the second file's path already existed at the destination, blitcp counted the link as done (“Links: 1 already exist”) without looking at what that file held. A source file that was changed so that it matched another file kept its old content in the backup, and so did a first run into a destination that already had other bytes at that path. A plain re-run never corrected it.

2. A change to one twin was written into both. Where the two linked files share one file on disk (hard links), that file belongs to both names. When one of the source files later changed, blitcp wrote the new content into that shared file — so the file that had not changed got the other file's content. Verification checks what the run wrote, so it passed. Re-running with --no-dedup or --overwrite only moved the wrong content from one name to the other.

Who is affected

You can be affected if deduplication was on (the default) and your source has, or at an earlier run had, files with identical content.

ModeFault 1 (twin skipped)Fault 2 (written into both)
local → localyesyes
local → SSH (push)yesonly when the destination host has no tar
SSH → local (pull)yesyes
SSH → SSHyesonly when the destination host has no tar
local → SMB (smb://)nono
local → S3, Azure, Google Cloud Storagenono

Runs with --no-dedup never hit fault 1. Fault 2 needs twins that an earlier run linked; once they are linked, a later run with or without --no-dedup can hit it.

Not affected: SMB and cloud destinations — blitcp makes no links there, and every file is checked or uploaded on its own (measured with 4.2.15 against a Samba share and S3, Azure and Google Cloud Storage emulators). Also not affected: content that already exists elsewhere on the destination while the source has no twin of it.

Filesystems. Fault 2 needs twins that share one file. Where the destination filesystem supports reflinks, blitcp clones twins instead, and they are separate files: on XFS fault 1 occurred and fault 2 did not. We measured on ext4 (hard links) and XFS (reflinks), not on btrfs, NTFS, APFS or exFAT.

What was measured. Both faults were reproduced on Linux with 2.1.0 (local) and 4.2.15 (local, push, pull, SSH to SSH, and push and SSH to SSH to a host without tar). Push and SSH-to-SSH to a BusyBox (Alpine 3.20) host: not affected by fault 2; Synology's own tar was not measured. Windows and macOS were not measured. The checks are the same code on every platform, and the copy engines open destination files through the same functions; what differs is how twins are linked (hard links on NTFS, clones on APFS).

How to check a backup

Compare every file in the backup with the source. Do this while the source is as it was at the last backup run: a file changed since then shows up as different too. A list of identical files in the source today is not enough — with fault 2, the twins may no longer be identical.

Source and backup on the same machine

Linux:

diff -rq /path/to/source /path/to/backup

Each Files … differ line is a file to repair. Only in /path/to/backup lines are blitcp's own files (.blitcp_dedup.db) or files no longer in the source.

macOS:

cd /path/to/source && find . -type f -print0 | xargs -0 shasum -a 256 > ~/blitcp-check.sha256
cd /path/to/backup && shasum -a 256 -c --quiet ~/blitcp-check.sha256

Windows (PowerShell):

$s = (Resolve-Path -LiteralPath 'C:\path\to\source').Path
$d = (Resolve-Path -LiteralPath 'D:\path\to\backup').Path
Get-ChildItem -LiteralPath $s -Recurse -File | ForEach-Object {
  $rel = $_.FullName.Substring($s.Length).TrimStart('\', '/')
  $t = Join-Path $d $rel
  if (-not (Test-Path -LiteralPath $t) -or
      (Get-FileHash -LiteralPath $_.FullName).Hash -ne (Get-FileHash -LiteralPath $t).Hash) { $rel }
}

Each name printed is a file to repair.

Backup on another machine (SSH)

Make a list on the machine that has the source, then check it on the machine that has the backup. Each FAILED line is a file to repair.

Source on Linux, backup over SSH (a push):

cd /path/to/source && find . -type f -print0 | xargs -0 sha256sum > ~/blitcp-check.sha256
ssh user@host 'cd /path/to/backup && sha256sum --quiet -c -' < ~/blitcp-check.sha256

Source on a Mac: use shasum -a 256 in place of sha256sum on the Mac, and on the other machine if it is a Mac too.

Source over SSH, backup on this Linux machine (a pull):

ssh user@host 'cd /path/to/source && find . -type f -print0 | xargs -0 sha256sum' > ~/blitcp-check.sha256
cd /path/to/backup && sha256sum --quiet -c ~/blitcp-check.sha256

Source on Windows (PowerShell), backup on a Linux host: make the list, copy it over and check it there.

$s = (Resolve-Path -LiteralPath 'C:\path\to\source').Path
$lines = Get-ChildItem -LiteralPath $s -Recurse -File | ForEach-Object {
  $rel = $_.FullName.Substring($s.Length).TrimStart('\', '/').Replace('\', '/')
  '{0}  ./{1}' -f (Get-FileHash -LiteralPath $_.FullName).Hash.ToLower(), $rel
}
[IO.File]::WriteAllText("$HOME\blitcp-check.sha256", ($lines -join "`n") + "`n")
scp "$HOME\blitcp-check.sha256" user@host:
ssh user@host 'cd /path/to/backup && sha256sum --quiet -c ~/blitcp-check.sha256'

Backup on Windows, source on a Linux host: make the list there with the pull command's first line, copy it here, then:

$d = (Resolve-Path -LiteralPath 'D:\path\to\backup').Path
Get-Content -LiteralPath "$HOME\blitcp-check.sha256" | ForEach-Object {
  $hash, $rel = $_ -split '  ', 2
  $t = Join-Path $d $rel.Substring(2)
  if (-not (Test-Path -LiteralPath $t) -or
      (Get-FileHash -LiteralPath $t).Hash -ne $hash.ToUpper()) { $rel }
}

What to do

  1. Update to 4.2.16.
  2. Run the same command you use for the backup, once. 4.2.16 compares every linked file whose path already exists, and never writes into a file that has another name, so the run writes the files that are wrong. In every case we reproduced — both faults, every mode listed above as affected, including hosts without tar — that one run left every file correct (measured on Linux).
  3. Run the check above again to confirm.

Do not use --no-dedup or --overwrite as a fix on an older version. With fault 2 they move the wrong content from one file to its twin.

One case stays as it was: a file on an SSH destination that was changed outside blitcp and kept its size. blitcp's signed hash cache on that destination still records it as unchanged, in 4.2.16 as in every earlier version. If the check lists such a file, delete it on the destination and run the backup again.

What changed in 4.2.16

A linked twin whose path already exists is compared with its source by size and content, like any other file, and written if it differs. It is not read again only when it is the same file as its original's and that file was confirmed unchanged in the same run. A local destination file that has more than one name is replaced, never written into; over SFTP every file is written under a temporary name and renamed into place, so the other names keep their content.

Re-run time: with hard links, an unchanged re-run takes about as long as in 4.2.15 (measured on ext4). Where twins are reflinks they are separate files and each one is read on every run: on XFS, an unchanged re-run with 80 duplicate 50 MB files took 67 s instead of 1.3 s.

New tests cover both faults in all four modes, including a destination left wrong by an earlier version. Every case that 4.2.15 got wrong was confirmed to fail on the code before the fix.

Why it was not caught

Verification checks the files a run writes. A file the run skipped as already linked was never read, and a file whose shared copy changed under it was not one the run wrote under that name. Both ended as “up to date” or “verified” over content nobody had compared.
