One copy, several destinations

blitcp 4.4.0 reads a folder once and writes it to several places at the same time — two external drives, a NAS over SSH, an SMB share, a bucket — and checks every one of them. Free and open source, on Linux, macOS and Windows, from the command line or the desktop app.

Details may change before release. What follows is taken from the 4.4.0 development branch.

What it does

  • One read of the source. Each file is read once and the same data goes to every destination at the same time.
  • Local, SSH, SMB and cloud, in any mix. A destination can be a local folder, an SSH folder (user@host:/path), an SMB share (smb:// or a UNC path), an s3://, az:// or gs:// prefix, or a saved connection (NAME:path).
  • Every destination checked. Each one is verified at the level it offers, and reported separately.
  • A manifest at each destination. An ASC MHL manifest and a blitcp.xxh128 file are kept there, so the next run skips what is already in place and a destination can be checked again later without the source.
  • One slow drive does not stop the rest. A destination that stalls is marked failed and the others carry on.

Who it is for

  • Photo and video card offload. Two copies of the card before it is formatted, both checked. Offloading camera cards →
  • Backup to two drives. One on the desk, one that leaves the building, written in the same run.
  • A NAS and the cloud. The NAS over SSH or SMB and a bucket off-site, from a single read of the source.

From the command line

Each destination is given with --dest. With --dest, every other path on the line is a source:

# a card to two drives
blitcp /media/CARD01 --dest /mnt/shuttle --dest /mnt/archive

# a local drive and a NAS over SSH
blitcp ~/Projects --dest /mnt/usb/backup --dest user@host:/backup

# a drive, a bucket and an SMB share
blitcp ~/Photos --dest /mnt/a --dest s3://bucket/backup --dest smb://nas/share/backup

# check a destination again later, without the source
blitcp --verify-manifest /mnt/shuttle
OptionWhat it does
--dest DESTA destination; repeat for several.
--dests-file FILEDestinations from a file, one per line; empty lines and lines starting with # are skipped.
--resumeContinue an interrupted run: files already written whose size, time and xxh128 still match the source are not copied again.
--overwrite-changedReplace a file the destination's manifest records with different content. By default it is kept and reported — cameras restart clip names on every card.
--deep-verify DESTVerify that destination by downloading every file it was sent and hashing it (all for every destination).
--verify-manifest DESTCheck a destination against its own manifest, without the source. Writes nothing. --deep reads every file back instead.
--fanout-buffer MBMemory for data read but not yet written everywhere (default 256). When it is full, the slowest destination sets the pace.
--stall-timeout SECONDSA destination with no progress for this long is marked failed and the others carry on (default 120).

How each destination is checked

DestinationCheck
Local folderevery file read back and compared with the source's hash
SSH folderthe remote host hashes each file it was sent (xxh128sum, sha256sum, Python or md5sum); without one of those, files are read back over SFTP
SMB shareevery file read back over the network
S3 and S3-compatiblethe store's own checksum: SHA-256 under 8 MiB, a full-object CRC for larger, multipart objects
Google Cloud Storagethe store's MD5
Azure Blobthe store's MD5 under 8 MiB; size only for larger blobs, unless the destination is named with --deep-verify

The summary names the level each destination reached. It says Verified only where content was compared, and “present, sizes match — content not compared” otherwise. For Azure video offloads, name the Azure destination with --deep-verify:

blitcp /media/CARD01 --dest /mnt/shuttle --dest az://media/2026-11-06 \
       --deep-verify az://media/2026-11-06

In the desktop app

“Add destination” opens a dialog for a local folder, an SSH folder, an SMB share or a bucket, with the same browsers and saved connections as everywhere else in the app. A list of destinations can be saved as a preset — paths only, never a credential — and comes back with “Run again”. While it runs there is one row per destination with its progress, speed, ETA and the level its verification reached.

Not with several destinations yet

--dry-run, --log-file and --use-sudo stop a --dest run with a one-line message before anything is written. The desktop app says what a multi-destination run does not take before it starts.

Questions

Can I use this today?

Not in a release yet. It is in development for blitcp 4.4.0; the current release is 4.2.15. Until then, copy to each destination in its own run — each run is verified.

Is the source read once or once per destination?

Once. Each file is read a single time and the same data is written to every destination at the same time. When the memory set aside for that (--fanout-buffer, 256 MB by default) is full, the slowest destination sets the pace.

What happens if one destination fails or hangs?

A destination that makes no progress for --stall-timeout seconds (120 by default) is marked failed and the others carry on. The summary reports each destination separately.

How is each destination verified?

At the level that destination offers. A local folder is read back and compared with the source. An SSH host hashes the files itself, or they are read back over SFTP. An SMB share is read back over the network. A bucket is checked against the checksum the store computed. The summary says Verified only where content was compared.

Is it free, and on which systems?

Yes, like the rest of blitcp: Apache-2.0, no paid tier, on Linux, macOS and Windows, from the command line or the desktop app.
