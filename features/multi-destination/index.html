One copy, several destinations

blitcp writes a folder to several places in one run — two external drives, a NAS over SSH, an SMB share, a bucket — and checks every one of them. Local, SSH and SMB destinations share one read of the source; cloud storage reads it on its own. Free and open source, on Linux, macOS and Windows, from the command line or the desktop app.

What it does

  • One read for local, SSH and SMB. Local, SSH and SMB destinations share one read of the source: each file is read once and the same data goes to all of them at the same time. Cloud storage reads it on its own.
  • Local, SSH, SMB and cloud, in any mix. A destination can be a local folder, an SSH folder (user@host:/path), an SMB share (smb://server/share/path), an s3://, az:// or gs:// prefix, or a saved connection (NAME:path).
  • Every destination checked. Each one is verified at the level it offers, and reported separately.
  • A manifest at each destination. With --manifest, each destination whose check found no fault gets an ASC MHL generation (ascmhl/ and blitcp.xxh128), so it can be checked again later without the source.
  • One slow drive does not stop the rest. A destination that stalls is marked failed and the others carry on.
  • Checked before the copy. Every destination is probed first; one that cannot be used is reported in one line, with what to fix. blitcp creds test NAME runs the same probe on a saved connection.

Who it is for

  • Photo and video card offload. Two copies of the card before it is formatted, both checked. Offloading camera cards →
  • Backup to two drives. One on the desk, one that leaves the building, written in the same run.
  • A NAS and the cloud. The NAS over SSH or SMB and a bucket off-site, in one run; the bucket reads the source on its own.

From the command line

Each destination is given with --dest. With --dest, every other path on the line is a source:

# a card to two drives, a folder per card on each
blitcp /media/CARD01 --dest /mnt/shuttle/2026-11-26_CARD01 --dest /mnt/archive/2026-11-26_CARD01

# a local drive and a NAS over SSH
blitcp ~/Projects --dest /mnt/usb/backup --dest user@host:/backup

# a drive, a bucket and an SMB share
blitcp ~/Photos --dest /mnt/a --dest s3://bucket/backup --dest smb://nas/share/backup

# with a manifest, then check a destination later, without the source
blitcp ~/Photos --dest /mnt/a --dest /mnt/b --manifest
blitcp --verify-manifest /mnt/a
OptionWhat it does
--dest DESTA destination; repeat for several. Local, SSH and SMB destinations share one read of the source; cloud storage reads it on its own.
--dests-file FILEDestinations from a file, one per line, as if each were given with --dest; empty lines and lines starting with # are skipped.
--manifestWrite an ASC MHL generation (ascmhl/ and blitcp.xxh128) at each destination whose check found no fault. What is skipped is decided as without it.
--verify-manifest DESTCheck a destination against its own manifest, without the source, at the level it offers. Writes nothing.
--deepWith --verify-manifest on an SSH, SMB or object-store destination: download every file and hash it here, instead of asking the remote host or the store.
--stall-timeout SECONDSA destination with no progress for this long is marked failed and the others carry on (default 120). It goes with several destinations; with one it is refused.
--ui dashboardA full-screen view with the phases, a rate graph and a row per destination. --no-color for one without colours.

For Azure video offloads, copy with --manifest, then check the container with --verify-manifest … --deep, which downloads every blob and hashes it:

blitcp /media/CARD01 --dest /mnt/shuttle/2026-11-26_CARD01 --dest az://media/2026-11-26_CARD01 --manifest
blitcp --verify-manifest az://media/2026-11-26_CARD01 --deep

In the desktop app

“Add destination” adds a local folder, an SSH folder, an SMB share or a bucket, with the same browsers and saved connections as everywhere else in the app. A list of destinations can be saved as a preset — paths only, never a credential. While it runs there is one row per destination with its verdict, and “Verify against manifest” checks a destination later. The manifest and stall-timeout options are in the app too.

Dry runs, logs and sudo with several destinations

  • --dry-run works: it shows each destination's plan, one after the other, and writes nothing there.
  • --log-file takes one destination for now; with several, the run is refused in one line (exit 2) before anything is written.
  • --use-sudo works with several local destinations. SSH, SMB and cloud destinations, and a remote source, are refused before the password is asked for.

Questions

Is the source read once or once per destination?

Once for local, SSH and SMB destinations: each file is read a single time and the same data is written to all of them at the same time. Cloud storage (S3, Azure, GCS) reads the source on its own.

What happens if one destination fails or hangs?

A destination that makes no progress for --stall-timeout seconds (120 by default) is marked failed and the others carry on. The summary reports each destination separately.

What if a destination already has a file with the same name?

If its content is different, it is replaced, without a warning — with or without --manifest, with one destination or several, as in 4.2.15. For camera cards, which reuse clip names, give each card its own folder: --dest /mnt/shuttle/2026-11-26_CARD01.

How is each destination verified?

At the level that destination offers. A local folder is read back from the disk. An SSH host hashes a random sample of the files itself. An SMB share is checked by size only. A bucket is checked against the checksum the store computed; Azure keeps none for a blob uploaded in blocks, which is checked by size. The summary says Verified only where content was compared.

Is it free, and on which systems?

Yes, like the rest of blitcp: Apache-2.0, no paid tier, on Linux, macOS and Windows, from the command line or the desktop app.
