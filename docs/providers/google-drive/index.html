Google Drive

blitcp copies folders to another drive, a NAS, another machine or cloud storage and verifies every file arrived. Google Drive has no usable API for that, but its desktop client mirrors everything to a local folder — and a local folder is where blitcp is strongest. Copy into it with verification on; Google's client handles the upload.

Where the folder lives

OSPath
WindowsG:\My Drive\
Drive for desktop mounts a drive letter by default
macOS~/Library/CloudStorage/GoogleDrive-<account>/My Drive/
Linux—
no official client; rclone or a third-party mount

Copy into it

blitcp --no-dedup ~/Photos ~/Google Drive/Photos

Verification runs by default: every file is read back from the destination and compared against the source before blitcp reports success.

Deduplication in a sync folder

Pass --no-dedup when the destination is inside a synced folder. blitcp deduplicates with hard links on NTFS and ext4, and sync clients handle those badly — Microsoft's own guidance is that later edits to a hard-linked file are not synced reliably. A shared inode also means editing one copy changes the other, which is not what anyone expects inside a folder like this.

There is nothing to gain either way: the client uploads both paths regardless, so the saving would only ever be local disk.

On APFS, btrfs and ReFS blitcp uses reflinks instead. Those are copy-on-write, so the copies stay independent and the problem does not arise — the run banner names the strategy it chose on the Dedup: line.

What blitcp does and does not promise

Drive for desktop offers two modes. Mirror keeps a real copy on disk, which is what blitcp needs. Stream keeps placeholders and fetches on demand — copying into a streamed folder works, but reading back out of one will pull every file down again, so verification of an existing copy can cost a full download.

The boundary is worth stating plainly: blitcp verifies the copy into the folder. Whether Google then uploads it correctly, and whether it is still intact months later, belongs to Google's client and not to blitcp. If you want a backup verified end to end, and one you can restore in full without paying egress, that is what the S3-compatible targets are for.
