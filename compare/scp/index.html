blitcp and scp, side by side

blitcp is an open-source copy tool — CLI and desktop app — that moves a folder to another drive, a NAS, another machine or cloud storage and verifies every file arrived. scp moves files over SSH too. On the run below they finished within seconds of each other over the same link. The difference is not speed — it is what you have once the copy stops.

Use blitcp when

You want the copy checked: every file read back and compared against the source, duplicates hard-linked instead of re-sent, and the next run skipping what has not changed. On a Linux destination that cost no measurable extra time.

Use scp / SFTP when

The destination is a network share or a Windows drive, where per-file checks are expensive and scp finished ahead — or it is one file, or a locked-down gateway with no exec channel, where --sftp-only makes blitcp do what scp already does.

What was measured

The same tree both times — 1,098 files, 1.1 GB, Linux, over SSH on a LAN — copied to two destinations that differ only in how expensive their metadata operations are.

On a normal Linux destination the two tools are, for practical purposes, the same speed: blitcp with verification, dedup and incremental skipping all switched on came in at 1m50.4s against scp’s 1m55.4s. That is a difference you would not notice and we are not going to sell you. The structural argument — one tar stream instead of a round-trip per file — did not turn into wall-clock time on this link. It may on a slower or higher-latency one. That has not been measured, so there is no number here for it.

Where the time actually went

Inside that tree sit 854 small files weighing 6.0 MB — about half a percent of the data. They moved at 6.7 MB/s to ext4 and 65.5 KB/s to the Windows drive: the same files, a factor of roughly a hundred apart, decided entirely by how much the destination charges per file rather than per byte.

Both tools pay that toll. They do not pay the same amount of it: moving from ext4 to drvfs cost scp 1.51× and blitcp 2.47×, with dedup and verification already off in both blitcp figures. The extra penalty is ours. blitcp does more metadata work per file than scp does, and on a filesystem where each of those operations is expensive, that work is what you are waiting for. It is a real cost of the checks, not a measurement artefact.

A larger tree, with no scp time beside it

Separately from everything above, and on a different tree: 91,663 files weighing 888 MB, pushed local → remote over a 100 Mbps LAN. Two sizes matter here and the table carries both: dedup meant only 509.8 MB was ever put on the wire.

Dedup found 46,951 duplicates and hard-linked them on the far side instead of sending them again, so 509.8 MB of the 888 MB actually crossed the wire, in 6 tar batches, with every file verified afterwards. That makes the link rate 4.0 MB/s, not the 888 MB ÷ 2m07.0s that the headline figures invite you to divide. The tree number is what you moved; the wire number is what the network carried. Quoting the first as though it were the second is how a 100 Mbps link ends up looking faster than it is.

No scp counterpart was measured on this tree. That is blitcp’s own time and nothing else — there is no multiplier here and none is implied. Nor does the result further up transfer to it. 854 small files is not 91,663 files with half of them duplicated; two orders of magnitude in file count is a different regime, not a larger version of the same one. What happens to either tool at that size, against each other, is unmeasured.

When scp is the better tool

The destination is a network share or a Windows drive. SMB, NFS, and a Windows filesystem reached through WSL all charge heavily per file. On the /mnt/c (WSL drvfs) destination measured above, scp finished in 2m54.1s against blitcp’s 4m29.3s — 35% less time, from the per-file checks blitcp performs and scp does not. If the destination is of that kind and you do not need those checks, scp is the faster choice and we would rather say so here than have you find out.

One file, once. scp file host: is unbeatable in keystrokes and is already installed on the machine. Nothing below the size of a directory tree is worth a download.

The far side is locked down. No exec channel means no tar can run there. blitcp falls back with --sftp-only, but at that point it is doing what scp does, with scp already present.

And if what you need is sub-file delta sync of large files that change slightly, that is neither tool — see blitcp vs rsync.
