Compare/blitcp vs rsync

An rsync alternative for first copies

blitcp is an open-source copy tool — CLI and desktop app — that moves a folder to another drive, a NAS, another machine or cloud storage and verifies every file arrived. rsync keeps two trees in step. Here is where each one wins.

Use blitcp when

It is the first full copy — a new backup drive, a new machine, a migration. Thousands of files that have never been written to the destination, especially on a spinning disk or over SSH.

Use rsync when

You are running the same copy again and most files have not changed, or you need mirroring with deletes, or snapshot chains with --link-dest.

The measured difference

12,347 files, 110.9 MB (9 KB average), rotational XFS source to SSD destination. Page cache dropped before every run; timing includes sync -f, so this is a durable copy, not a buffer race. Best of three interleaved rounds; dedup off so both tools write the same bytes:

ToolTimeThroughput
blitcp (verify ON)8.19 s13.5 MB/s · 1,507 files/s
rsync -a14.14 s7.8 MB/s · 873 files/s

With dedup on, the same job finishes in 5.93 s — but that is no longer an apples-to-apples write comparison. Full methodology and every command here.

Why the first copy is where the gap is

On a spinning disk most of the time in a small-file copy is not spent reading data — it is spent moving the head between files. rsync, like cp, reads files in directory order, which has nothing to do with where they sit on the platter. blitcp asks the filesystem where each file's data lives (FIEMAP on Linux) and reads in that physical order, so the head sweeps across the disk instead of jumping back and forth.

That matters most exactly when rsync's strength does not apply: the destination is empty, so there are no unchanged files to skip and no blocks to delta. Every byte has to be read once either way; the only question is how much seeking it costs. On NVMe there is no seek to save, which is why the two tools are close there.

When to use rsync, when to use blitcp

Most people who look for an rsync alternative do not need to give rsync up. The two tools are good at different moments in the life of a backup:

SituationReach for
First copy to a new backup drive, a new machine, a migrationblitcp
Thousands of small files on a spinning diskblitcp
The copy has to be checked, without a second pass of your ownblitcp — verification is on by default
The far end is a Synology or BusyBox box with no rsyncblitcp — it needs only ssh and tar there
The destination is S3, Azure or Google Cloud Storageblitcp — rsync has no cloud endpoints
Windows, without Cygwin or WSLblitcp
Nightly re-run where most files have not changedrsync
Large files that change a little between runsrsync — it sends only the changed blocks
Mirroring, deletions includedrsync
Snapshot chains with --link-destrsync
Full copy, NVMe to NVMeeither — they are close

blitcp does have incremental runs: a second run skips files whose content it has already seen, using its hash cache, and duplicates inside the tree are written once and hard-linked. What it does not have is rsync's sub-file delta transfer, mirroring or snapshot rotation.

What a copy looks like

Source first, destination second — the same order as cp. Nothing in the source is modified, verification runs by default, and blitcp refuses to start if the destination is too small:

blitcp /data /media/usb/data                # local → local
blitcp /data user@host:/backup              # local → remote over SSH
blitcp user@host:/data s3://bucket/backup   # SSH → cloud

More in the local copies and SSH transfers guides.

When rsync is still the better tool

Honest answer: repeated syncs of mostly-unchanged trees. rsync's delta algorithm transfers only changed blocks, and --link-dest snapshot chains are a proven backup pattern. blitcp skips unchanged files entirely (hash cache), but it does not do sub-file deltas. On NVMe-to-NVMe the block-ordering advantage also mostly disappears — there, the tools are close for full copies and rsync wins the incremental case.

Questions

Is blitcp an rsync alternative?

For a first full copy, yes: a new backup drive, a new machine, a migration. On 12,347 small files from a spinning disk to an SSD, cold cache, blitcp took 8.19 s with verification on and rsync -a took 14.14 s. For repeated syncs of mostly unchanged trees, rsync remains the better tool.

When should I still use rsync?

When you run the same copy again and most files have not changed: rsync's delta algorithm sends only changed blocks, and blitcp does not do sub-file deltas. Also when you need mirroring with deletes, or --link-dest snapshot chains. On NVMe to NVMe the two are close for full copies and rsync wins the incremental case.

Does blitcp need anything installed on the remote server?

Only ssh and tar, which BusyBox systems and Synology NAS boxes already have. rsync needs the rsync binary on both ends.

Does blitcp run on Linux, macOS and Windows?

Yes, natively on all three, as a command-line tool and as a desktop app. rsync on Windows needs Cygwin or WSL.

Is blitcp free for commercial use?

Yes. blitcp is open source under the Apache-2.0 license, which allows commercial use, and there is no paid tier: the CLI and the desktop app are the whole tool.
